# Storage measurements (Stage 12.5)

## Method and reproducibility

Run `bash scripts/ci-integration.sh storage-release` from the repository root.
The fixture is generated by the real ETL, backed up and restored to a second
disposable cluster before any performance seeding. The observer then copies
10,000 synthetic SQL-shape rows into each of seven existing tables on the restored
clone only. Every row satisfies storage constraints; copied JSON payloads are
intentionally not rewritten to describe the synthetic identity. No application
worker may consume this measurement dataset.

Each seeded queue has 9,900 terminal, 50 pending, 25 expired in-flight and 25 failed
rows for chain 777. The original chain-1 fixture retains seven candidates across
the reorg, 14 transactions, 14 receipts and seven logs. Seeded tables therefore
have 10,007 rows: Extractor raw/outbox; Transformer inbox/results/outbox; Loader
inbox/blocks. ANALYZE runs after each insert; autovacuum is not disabled. This is
a mostly completed-history workload with 75 eligible claims, not a high-backlog
stress or concurrency benchmark.

Claims, capacity and metrics SQL are selected from the current PostgreSQL adapters
using Go's parser, with fixed synthetic bind values substituted as SQL literals.
This does not measure PostgreSQL generic prepared-statement plans. Inbox claim RETURNING is
reduced to `event_id`; payload transport/decoding is not timed. Loader height and
neighbor SELECTs measure the relevant primary-key access path, not its complete
multi-statement persistence transaction. Every DML EXPLAIN runs in a transaction
that is rolled back. Aborted updates can still generate WAL/dead tuples and warm
caches on this disposable clone. The original fixture's complete snapshot is
checked again after measurement.

Three `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` samples per query are retained.
The seeded workload has already warmed buffers; these are not cold-cache results,
percentiles, throughput or Mainnet capacity estimates. Planner costs are not
milliseconds. Reported execution time is PostgreSQL's instrumented statement time,
excluding Docker startup, client latency and planning. See
[PostgreSQL EXPLAIN caveats](https://www.postgresql.org/docs/17/using-explain.html).

## Observed baseline — 2026-10-26

Environment reported by PostgreSQL: **17.11**, Debian 12, **x86_64 Linux**, default
`shared_buffers=128MB`, `work_mem=4MB`. Total measured database size: **138,925,747
bytes**. This is the observed container platform; it does not certify native
Apple Silicon performance. Full plans and relation sizes are in
[machine-readable evidence](../measurements/stage12-storage.json).

For sample 1, every listed root plan reports zero shared reads and zero temporary
read/write blocks. Hit counts are root totals, not sums over children. Claim plans
sort 75 eligible rows and use both partial indexes; they do not scan all retained
terminal events. The expired index can include an aborted prior sample's tuple
before visibility checks. Capacity scans 10,007 Outbox rows, discards 9,907 and
joins 100 outstanding rows. Its raw-byte calculation deliberately includes failed
events, matching backpressure semantics.

Metric queries must count terminal as well as outstanding rows. Sequential scans
are expected for this selectivity; an index on status alone would not eliminate
the complete-count work. Transformer Outbox metrics must join its own result and
Inbox to identify chain, making it the slowest measured statement. At this size,
the full scan remains below the one-second snapshot timeout, but this gives no
guarantee at millions of retained rows or under concurrent load.

## Optimization decision

**No production query or index changes are justified by this baseline.** Existing
partial claim indexes and Loader primary key are used. Adding an index would add
write/storage cost, require a new owned migration/readiness manifest and still
would not remove the all-history metric aggregates. No speculative index,
denormalized counter, partitioning or retention feature was added.

The measured follow-up risks are growing metric scan cost and capacity scans,
large backlogs requiring larger claim sorts, wider payload/TOAST costs, and
per-chain serialization. Before an optimization, measure real retained size,
backlog distribution, cold and warm caches, concurrent workers, lock waits,
autovacuum activity, actual transaction/log cardinalities and representative
Mainnet payload widths. Compare identical workloads before/after and include
index size/write overhead, not only SELECT latency. Do not extrapolate these
three samples into a production SLO.

## Backup/restore evidence

The successful baseline restored **100,986 bytes** of custom-format archive into
a fresh PostgreSQL cluster. SHA-256:
`9b6db74819d5035c29ab12efdd36ad6608397fdeaccc4cfca65106540ed1548b`.
The dump command took **293.324017 ms**, restore **635.260368 ms**; provisioning,
copying and verification are excluded. Complete row hashes and schema/ACL/role
metadata matched, runtime authentication succeeded, foreign-schema reads were
denied, a populated destination was rejected, and the original source snapshot
was unchanged. Storage subtest: **102.78 s**; full E2E including storage: **125.64 s**.
Archive bytes/digest vary between runs because fixture timestamps and state are
new each time; this digest identifies this measurement run only.

Raw archives and private credentials remain outside Git. The retained report is
not the backup itself. The [restore runbook](backup-restore-stage12.md) explicitly
limits these results to same-version local logical recovery, without PITR,
off-host disaster or production RPO/RTO certification.
